## Singleton Design Pattern

The **Singleton Pattern** is a creational design pattern that ensures:

> **A class has only one instance throughout the application and provides a single, global way to access that instance.**

### Real-time example: Application Configuration

Imagine an ASP.NET Core application that reads configuration from `appsettings.json`.

You don't want every part of your application to create a new configuration manager:

```text
Controller → new ConfigurationManager()
Service    → new ConfigurationManager()
Repository → new ConfigurationManager()
```

Instead, you want **one shared instance**:

```text
             ┌──────────────────┐
             │ Configuration    │
             │ Manager          │
             │  ONE INSTANCE    │
             └────────┬─────────┘
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
     Controller     Service    Repository
```

### Simple C# implementation

```csharp
public sealed class AppConfiguration
{
    private static AppConfiguration? _instance;

    private AppConfiguration()
    {
    }

    public static AppConfiguration Instance
    {
        get
        {
            if (_instance == null)
                _instance = new AppConfiguration();

            return _instance;
        }
    }

    public string ApplicationName { get; set; } = "MyApp";
}
```

Usage:

```csharp
var config1 = AppConfiguration.Instance;
var config2 = AppConfiguration.Instance;

Console.WriteLine(config1 == config2);
```

Output:

```text
True
```

Both variables point to **the same object**.

---

## Why `private constructor`?

```csharp
private AppConfiguration()
{
}
```

This prevents other classes from doing:

```csharp
var config = new AppConfiguration(); // ❌ Not allowed
```

They must use:

```csharp
AppConfiguration.Instance
```

Therefore, the class controls how its instance is created.

---

## Important interview point: Thread Safety

The above implementation isn't ideal in a multithreaded application because two threads could potentially create two instances simultaneously.

A safer implementation is:

```csharp
public sealed class AppConfiguration
{
    private static readonly Lazy<AppConfiguration> _instance
        = new Lazy<AppConfiguration>(() => new AppConfiguration());

    private AppConfiguration()
    {
    }

    public static AppConfiguration Instance => _instance.Value;
}
```

`Lazy<T>` provides **thread-safe lazy initialization**.

## Where do we use Singleton in real .NET applications?

Common examples include objects where **one shared instance is desirable**:

* Application-wide configuration
* Certain caching components
* Logging infrastructure
* Shared resource managers
* Expensive objects that should not be repeatedly created

In **ASP.NET Core**, you normally don't manually implement Singleton. Instead, you use the built-in **Dependency Injection container**:

```csharp
builder.Services.AddSingleton<IConfigurationService, ConfigurationService>();
```

Now ASP.NET Core creates **one instance for the application's DI container lifetime** and reuses it.

### Interview answer

> **Singleton is a creational design pattern that ensures only one instance of a class is created and provides a common access point to it. In ASP.NET Core, instead of implementing Singleton manually, we generally register services using `AddSingleton()` in the built-in Dependency Injection container. A practical example would be an application-wide configuration or shared resource manager where creating multiple instances isn't necessary.**

**One important distinction:** `Singleton` does **not** mean "one instance forever." In ASP.NET Core DI, `AddSingleton()` means one instance **for the lifetime of that DI container/application**.
