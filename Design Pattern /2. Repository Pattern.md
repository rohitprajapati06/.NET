## Repository Pattern in .NET

The **Repository Pattern** is a design pattern used to separate **data-access logic** from your **business logic**.

Think of it as:

> **Controller/Service → Repository → Database**

Instead of writing EF Core database queries directly inside your service/controller, you put them inside a Repository.

### 1. Without Repository

```csharp
public class PatientService
{
    private readonly AppDbContext _context;

    public PatientService(AppDbContext context)
    {
        _context = context;
    }

    public async Task<Patient?> GetPatient(int id)
    {
        return await _context.Patients
            .FirstOrDefaultAsync(x => x.Id == id);
    }
}
```

Here, `PatientService` knows about **EF Core and DbContext**.

---

## 2. With Repository

Create an interface:

```csharp
public interface IPatientRepository
{
    Task<Patient?> GetByIdAsync(int id);
    Task<List<Patient>> GetAllAsync();
    Task AddAsync(Patient patient);
}
```

Then implement it:

```csharp
public class PatientRepository : IPatientRepository
{
    private readonly AppDbContext _context;

    public PatientRepository(AppDbContext context)
    {
        _context = context;
    }

    public async Task<Patient?> GetByIdAsync(int id)
    {
        return await _context.Patients
            .FirstOrDefaultAsync(x => x.Id == id);
    }

    public async Task<List<Patient>> GetAllAsync()
    {
        return await _context.Patients.ToListAsync();
    }

    public async Task AddAsync(Patient patient)
    {
        await _context.Patients.AddAsync(patient);
        await _context.SaveChangesAsync();
    }
}
```

Now the service uses the repository:

```csharp
public class PatientService
{
    private readonly IPatientRepository _repository;

    public PatientService(IPatientRepository repository)
    {
        _repository = repository;
    }

    public async Task<Patient?> GetPatient(int id)
    {
        return await _repository.GetByIdAsync(id);
    }
}
```

The flow becomes:

```text
Controller
    ↓
PatientService
    ↓
IPatientRepository
    ↓
PatientRepository
    ↓
EF Core / DbContext
    ↓
Database
```

### Why use Repository Pattern?

**1. Separation of concerns**

Your business/service layer doesn't need to know how data is stored.

**2. Testability**

You can mock `IPatientRepository` during unit testing.

```csharp
var mockRepository = new Mock<IPatientRepository>();
```

You don't necessarily need a real database to test your service.

**3. Centralized data-access logic**

Queries related to `Patient` can stay in `PatientRepository`.

**4. Easier to change data-access implementation**

For example:

```text
Service
   ↓
IPatientRepository
   ↓
EF Core Repository
```

Later, the implementation could theoretically change without changing the service.

---

### Repository vs DbContext

This is important for interviews.

**DbContext already provides repository/unit-of-work-like functionality.**

EF Core's:

```csharp
_context.Patients
```

is essentially a collection through which you perform data access.

Therefore, **you don't always need to create a Repository on top of EF Core**. In modern ASP.NET Core applications, adding a repository purely to wrap simple EF Core calls can sometimes create unnecessary abstraction.

Use it when it provides a **real architectural benefit**—for example, complex data-access logic, a domain boundary, multiple data sources, or a requirement to isolate persistence concerns.

### Interview definition

> **Repository Pattern is a design pattern that abstracts data-access operations behind an interface, allowing the business layer to work with data without directly depending on the underlying database or ORM.**

For a .NET developer, you should understand **Repository + Unit of Work + Dependency Injection + EF Core**, because these concepts are commonly discussed together.
