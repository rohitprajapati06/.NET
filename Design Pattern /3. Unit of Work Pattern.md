## Unit of Work Pattern in .NET

The **Unit of Work (UoW) pattern** is used to **manage multiple database operations as a single transaction**.

In simple terms:

> **Unit of Work keeps track of all changes and commits them to the database together.**

### Real-time example

Suppose you're building an **Appointment Management System**.

When a patient books an appointment, you may need to:

1. Create an appointment.
2. Update the doctor's availability.
3. Create a payment record.

All three operations should succeed together.

If payment creation fails, you don't want the appointment and doctor's availability to be updated.

That's where **Unit of Work** helps:

```text
             Unit of Work
                  |
        ---------------------
        |         |         |
   Appointment  Doctor    Payment
   Repository  Repository Repository
        |         |         |
        --------Transaction-
                  |
              SaveChanges()
```

If everything succeeds:

```text
Commit Transaction
```

If something fails:

```text
Rollback Transaction
```

---

## Without Unit of Work

You might have:

```csharp
appointmentRepository.Add(appointment);
doctorRepository.Update(doctor);
paymentRepository.Add(payment);

appointmentRepository.Save();
doctorRepository.Save();
paymentRepository.Save();
```

The problem is that these operations may be committed separately.

If the third operation fails, the first two might already be saved.

---

## With Unit of Work

You have one central object responsible for committing changes:

```csharp
public interface IUnitOfWork
{
    IAppointmentRepository Appointments { get; }
    IDoctorRepository Doctors { get; }
    IPaymentRepository Payments { get; }

    Task<int> SaveChangesAsync();
}
```

Implementation:

```csharp
public class UnitOfWork : IUnitOfWork
{
    private readonly AppDbContext _context;

    public IAppointmentRepository Appointments { get; }
    public IDoctorRepository Doctors { get; }
    public IPaymentRepository Payments { get; }

    public UnitOfWork(
        AppDbContext context,
        IAppointmentRepository appointments,
        IDoctorRepository doctors,
        IPaymentRepository payments)
    {
        _context = context;
        Appointments = appointments;
        Doctors = doctors;
        Payments = payments;
    }

    public async Task<int> SaveChangesAsync()
    {
        return await _context.SaveChangesAsync();
    }
}
```

Then your service can do:

```csharp
public async Task BookAppointment(Appointment appointment)
{
    _unitOfWork.Appointments.Add(appointment);

    var doctor = await _unitOfWork.Doctors.GetById(appointment.DoctorId);

    doctor.IsAvailable = false;

    _unitOfWork.Doctors.Update(doctor);

    _unitOfWork.Payments.Add(new Payment());

    await _unitOfWork.SaveChangesAsync();
}
```

The important point is that **all changes are tracked by the same `DbContext` and saved together**.

### Unit of Work vs Repository

A common interview question:

| Repository                                 | Unit of Work                        |
| ------------------------------------------ | ----------------------------------- |
| Handles operations for a particular entity | Coordinates multiple repositories   |
| Example: AppointmentRepository             | Example: UnitOfWork                 |
| Add/Get/Update Appointment                 | Commit all changes                  |
| Focuses on data access                     | Focuses on transaction/coordination |

Think of it as:

```text
Repository = "Work with this entity"

Unit of Work = "Complete all these changes together"
```

### Important point for EF Core

**`DbContext` already implements the Unit of Work pattern** because it:

* Tracks entity changes
* Coordinates changes
* Provides `SaveChanges()`
* Can participate in transactions

So in modern ASP.NET Core applications, creating a custom Unit of Work isn't always necessary.

### Interview answer

> **"Unit of Work is a design pattern that coordinates multiple database operations and commits them as a single unit. For example, while booking an appointment, I may create an appointment, update doctor availability, and create a payment record. Unit of Work ensures these changes are committed together. If something fails, the transaction can be rolled back. In EF Core, DbContext itself already follows the Unit of Work pattern through change tracking and SaveChanges."**
