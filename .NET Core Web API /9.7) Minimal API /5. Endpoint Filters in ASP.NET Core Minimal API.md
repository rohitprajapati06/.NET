# Endpoint Filters in ASP.NET Core Minimal API

**Endpoint Filters** allow you to execute logic **before and/or after a Minimal API endpoint runs**.

They are similar in purpose to **action filters in MVC/Web API controllers**.

Common uses:

* Validation
* Logging
* Authorization checks
* Exception handling
* Request/response processing
* Cross-cutting concerns

---

## 1. Basic Endpoint Filter

Create a filter by implementing `IEndpointFilter`:

```csharp
public class LoggingFilter : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        Console.WriteLine("Before endpoint");

        var result = await next(context);

        Console.WriteLine("After endpoint");

        return result;
    }
}
```

Here:

```text
Request
   ↓
LoggingFilter
   ↓
Endpoint
   ↓
LoggingFilter
   ↓
Response
```

---

## 2. Register Filter with an Endpoint

Use `AddEndpointFilter<T>()`:

```csharp
app.MapGet("/products", () =>
{
    return Results.Ok("Products");
})
.AddEndpointFilter<LoggingFilter>();
```

Now `LoggingFilter` executes whenever this endpoint is called.

---

# 3. Filter Using `ILogger`

Instead of `Console.WriteLine`, use ASP.NET Core logging:

```csharp
public class LoggingFilter : IEndpointFilter
{
    private readonly ILogger<LoggingFilter> _logger;

    public LoggingFilter(ILogger<LoggingFilter> logger)
    {
        _logger = logger;
    }

    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        _logger.LogInformation("Request started");

        var result = await next(context);

        _logger.LogInformation("Request completed");

        return result;
    }
}
```

---

# 4. Accessing Endpoint Parameters

One useful feature is that a filter can inspect endpoint arguments.

Suppose:

```csharp
app.MapPost("/products", (Product product) =>
{
    return Results.Ok(product);
})
.AddEndpointFilter<ProductValidationFilter>();
```

The filter can access `Product`:

```csharp
public class ProductValidationFilter : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        var product = context.Arguments
            .OfType<Product>()
            .FirstOrDefault();

        if (product == null)
        {
            return Results.BadRequest("Product is required");
        }

        if (string.IsNullOrWhiteSpace(product.Name))
        {
            return Results.BadRequest("Product name is required");
        }

        if (product.Price <= 0)
        {
            return Results.BadRequest("Price must be greater than zero");
        }

        return await next(context);
    }
}
```

If validation fails:

```text
Request
   ↓
Filter
   ↓
Validation fails
   ↓
400 Bad Request
```

The endpoint itself is never executed.

---

# 5. Inline Endpoint Filter

You don't always need a separate class.

You can write:

```csharp
app.MapGet("/products", () =>
{
    return Results.Ok("Products");
})
.AddEndpointFilter(async (context, next) =>
{
    Console.WriteLine("Before endpoint");

    var result = await next(context);

    Console.WriteLine("After endpoint");

    return result;
});
```

This is useful for **small pieces of filter logic**.

---

# 6. Applying a Filter to Multiple Endpoints

You can use a route group:

```csharp
var products = app.MapGroup("/api/products")
    .AddEndpointFilter<LoggingFilter>();

products.MapGet("/", GetProducts);

products.MapGet("/{id}", GetProduct);

products.MapPost("/", CreateProduct);
```

Now the filter applies to all endpoints in the group.

This is particularly useful for organizing Minimal APIs.

---

# 7. Filter Execution Flow

Consider:

```csharp
app.MapGet("/products", () =>
{
    return Results.Ok();
})
.AddEndpointFilter<LoggingFilter>();
```

Execution is approximately:

```text
HTTP Request
     ↓
Endpoint Filter
     ↓
Before logic
     ↓
Endpoint Handler
     ↓
After logic
     ↓
HTTP Response
```

The important line is:

```csharp
var result = await next(context);
```

`next(context)` passes execution to the next filter or the actual endpoint.

If you don't call `next(context)`, the endpoint won't execute.

---

# 8. Endpoint Filters vs Middleware

They solve different problems.

| Endpoint Filter                | Middleware                       |
| ------------------------------ | -------------------------------- |
| Specific to endpoints          | Applies to HTTP pipeline         |
| Minimal API focused            | Entire application pipeline      |
| Can access endpoint arguments  | Works mainly with `HttpContext`  |
| Good for validation            | Good for global concerns         |
| Runs around endpoint execution | Runs around the request pipeline |

### Example

Use **Middleware** for:

```text
Global exception handling
Logging
Authentication pipeline
CORS
Request/response processing
```

Use **Endpoint Filters** for:

```text
Endpoint validation
Endpoint-specific logging
Checking endpoint parameters
Endpoint-specific authorization/business rules
```

---

# 9. Endpoint Filter Factory

For more advanced scenarios, you can create filters dynamically using `IEndpointFilterFactory`.

This is useful when the filter needs information about the endpoint's parameters at startup time.

For most applications, however, implementing:

```csharp
IEndpointFilter
```

is sufficient.

---

## Interview Answer

> **Endpoint Filters in ASP.NET Core Minimal API provide a way to execute logic before and after a Minimal API endpoint. They are similar to action filters in controller-based APIs. We can implement `IEndpointFilter` and register it using `AddEndpointFilter()`. They are commonly used for validation, logging, authorization checks, and other endpoint-specific cross-cutting concerns. Unlike middleware, endpoint filters can access the arguments passed to the endpoint.**
