# Error Handling and Logging in ASP.NET Core Minimal API

In a Minimal API, **error handling** and **logging** are important for preventing application crashes, returning proper HTTP responses, and troubleshooting production issues.

The two main approaches are:

* **Error Handling** → Handle exceptions and return meaningful HTTP responses.
* **Logging** → Record information, warnings, errors, and diagnostic details.

---

## 1. Basic Error Handling

You can handle expected errors directly in the endpoint:

```csharp
app.MapGet("/products/{id}", async (int id, AppDbContext context) =>
{
    var product = await context.Products.FindAsync(id);

    if (product == null)
        return Results.NotFound("Product not found");

    return Results.Ok(product);
});
```

Here, instead of throwing an exception, we return:

```text
404 Not Found
```

---

## 2. Global Exception Handling

For unexpected exceptions, use ASP.NET Core's global exception handler.

```csharp
var builder = WebApplication.CreateBuilder(args);

var app = builder.Build();

app.UseExceptionHandler("/error");

app.Map("/error", () =>
{
    return Results.Problem(
        title: "An unexpected error occurred.",
        statusCode: StatusCodes.Status500InternalServerError
    );
});

app.MapGet("/products", () =>
{
    throw new Exception("Database connection failed");
});

app.Run();
```

If an unhandled exception occurs, the request is redirected to the `/error` endpoint.

A more modern approach is to use `IExceptionHandler` for centralized exception handling.

---

# 3. Using `IExceptionHandler`

Create a custom exception handler:

```csharp
public class GlobalExceptionHandler : IExceptionHandler
{
    private readonly ILogger<GlobalExceptionHandler> _logger;

    public GlobalExceptionHandler(
        ILogger<GlobalExceptionHandler> logger)
    {
        _logger = logger;
    }

    public async ValueTask<bool> TryHandleAsync(
        HttpContext httpContext,
        Exception exception,
        CancellationToken cancellationToken)
    {
        _logger.LogError(
            exception,
            "Unhandled exception occurred.");

        await Results.Problem(
            statusCode: 500,
            title: "Internal Server Error"
        ).ExecuteAsync(httpContext);

        return true;
    }
}
```

Register it:

```csharp
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();
builder.Services.AddProblemDetails();
```

Then:

```csharp
app.UseExceptionHandler();
```

Now unexpected exceptions are handled centrally.

# 4. Logging in Minimal API

ASP.NET Core provides `ILogger<T>` through Dependency Injection.

Example:

```csharp
app.MapGet("/products", (
    ILogger<Program> logger) =>
{
    logger.LogInformation("Getting products");

    return Results.Ok(new[]
    {
        "Laptop",
        "Mobile",
        "Tablet"
    });
});
```

---

# 5. Different Log Levels

ASP.NET Core provides several log levels:

```csharp
logger.LogTrace("Trace message");

logger.LogDebug("Debug message");

logger.LogInformation("Information message");

logger.LogWarning("Warning message");

logger.LogError("Error message");

logger.LogCritical("Critical error");
```

Typical usage:

| Level       | Purpose                              |
| ----------- | ------------------------------------ |
| Trace       | Very detailed diagnostic information |
| Debug       | Development/debugging information    |
| Information | Normal application activity          |
| Warning     | Something unexpected but recoverable |
| Error       | An operation failed                  |
| Critical    | Serious application failure          |

---

# 6. Logging Exceptions

Always pass the exception object when logging an exception:

```csharp
try
{
    // Database operation
}
catch (Exception ex)
{
    logger.LogError(
        ex,
        "Error while retrieving products.");

    throw;
}
```

This preserves the exception details and stack trace.

---

# 7. Structured Logging

Instead of:

```csharp
logger.LogInformation(
    "Product {id} was requested",
    id);
```

you should prefer structured logging over string concatenation:

```csharp
logger.LogInformation(
    "Product {ProductId} was requested",
    id);
```

`ProductId` becomes a structured property that logging systems can search and filter.

---

# 8. Example: Error Handling + Logging

A practical Minimal API endpoint:

```csharp
app.MapGet("/products/{id}", async (
    int id,
    AppDbContext context,
    ILogger<Program> logger) =>
{
    try
    {
        logger.LogInformation(
            "Fetching product {ProductId}",
            id);

        var product = await context.Products.FindAsync(id);

        if (product == null)
        {
            logger.LogWarning(
                "Product {ProductId} was not found",
                id);

            return Results.NotFound();
        }

        return Results.Ok(product);
    }
    catch (Exception ex)
    {
        logger.LogError(
            ex,
            "Error fetching product {ProductId}",
            id);

        return Results.Problem(
            "An unexpected error occurred.");
    }
});
```

However, in a real application, you generally **shouldn't put `try-catch` in every endpoint**. Use centralized exception handling for unexpected exceptions.

# 9. Recommended Architecture

For a production Minimal API:

```text
Request
   ↓
Minimal API Endpoint
   ↓
Service
   ↓
Repository / EF Core
   ↓
Database
   ↓
Exception
   ↓
Global Exception Handler
   ↓
ILogger
   ↓
Log System
```

For example:

```text
Exception
    ↓
IExceptionHandler
    ↓
ILogger
    ↓
Serilog / Application Insights
```

This keeps your endpoints clean.

---

## 10. Important Interview Point

**Error handling and logging have different responsibilities:**

```text
Error Handling → What response should the client receive?

Logging → What happened inside the application?
```

For example:

```text
Client:
500 Internal Server Error

Server Log:
Database timeout while retrieving ProductId = 25
Exception: SqlException
```

The client should generally **not receive the internal exception details**, while the server logs should contain enough diagnostic information to investigate the problem.

### Interview Answer

> **In Minimal APIs, I handle expected errors using appropriate `Results` such as `Results.NotFound()` or `Results.BadRequest()`. For unexpected exceptions, I prefer centralized exception handling using `IExceptionHandler` or `UseExceptionHandler()`. For logging, I inject `ILogger` into the endpoint or service and use structured logging with appropriate log levels such as Information, Warning, Error, and Critical. In production, logs can be forwarded to systems such as Serilog or Azure Application Insights.**
