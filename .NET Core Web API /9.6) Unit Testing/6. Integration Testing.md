# Integration Testing in ASP.NET Core Web API

**Integration Testing** verifies that **multiple components of your application work together correctly**.

Unlike unit testing, integration testing doesn't isolate every dependency.

For an ASP.NET Core Web API, you can test the complete request pipeline:

```text
HTTP Request
     ↓
Controller
     ↓
Service / MediatR
     ↓
Repository
     ↓
EF Core
     ↓
Test Database
     ↓
HTTP Response
```

---

## 1. Unit Test vs Integration Test

| Unit Testing              | Integration Testing              |
| ------------------------- | -------------------------------- |
| Tests one component       | Tests multiple components        |
| Dependencies are mocked   | Real dependencies are often used |
| Very fast                 | Slower                           |
| No real database required | Test database commonly used      |
| Tests business logic      | Tests component integration      |
| Example: Service          | Example: API endpoint            |

### Example

**Unit test:**

```text
DoctorService
     ↓
Mock Repository
```

**Integration test:**

```text
HTTP Request
     ↓
DoctorsController
     ↓
DoctorService
     ↓
DoctorRepository
     ↓
EF Core
     ↓
Test DB
```

---

# 2. ASP.NET Core Integration Testing

ASP.NET Core provides:

```csharp
WebApplicationFactory<TEntryPoint>
```

through the package:

```text
Microsoft.AspNetCore.Mvc.Testing
```

It allows you to start your API application in a **test environment** and send HTTP requests to it.

You can then use:

```csharp
HttpClient
```

to call your endpoints.

---

# 3. Create Integration Test Project

Suppose your solution is:

```text
HealthcareAPI
│
├── HealthcareAPI
│
└── HealthcareAPI.Tests
```

You can create:

```text
HealthcareAPI.IntegrationTests
```

Install:

```bash
dotnet add package Microsoft.AspNetCore.Mvc.Testing
```

You may also need your database provider/test infrastructure depending on your application.

---

# 4. Create WebApplicationFactory

Create:

```text
CustomWebApplicationFactory.cs
```

```csharp
public class CustomWebApplicationFactory
    : WebApplicationFactory<Program>
{
}
```

This gives the integration test access to your ASP.NET Core application.

---

# 5. Create the Test Class

```csharp
public class DoctorsApiTests 
    : IClassFixture<CustomWebApplicationFactory<Program>>
{
    private readonly HttpClient _client;

    public DoctorsApiTests(
        CustomWebApplicationFactory<Program> factory)
    {
        _client = factory.CreateClient();
    }
}
```

Now the test can make actual HTTP requests.

---

# 6. Test a GET Endpoint

Suppose your API has:

```text
GET /api/doctors
```

Test:

```csharp
[Fact]
public async Task GetDoctors_ReturnsSuccessStatusCode()
{
    // Act
    var response = await _client.GetAsync("/api/doctors");

    // Assert
    response.EnsureSuccessStatusCode();
}
```

This sends a real HTTP request through the test server.

---

# 7. Check HTTP Status Code

Instead of:

```csharp
response.EnsureSuccessStatusCode();
```

you can explicitly verify:

```csharp
Assert.Equal(
    HttpStatusCode.OK,
    response.StatusCode);
```

So we're testing:

```text
GET /api/doctors
       ↓
ASP.NET Core Pipeline
       ↓
Controller
       ↓
Service
       ↓
Repository
       ↓
Database
       ↓
200 OK
```

---

# 8. Test Response Data

Suppose the endpoint returns:

```json
[
    {
        "id": "123",
        "name": "Dr. John",
        "specialization": "Cardiology"
    }
]
```

You can deserialize the response:

```csharp
var doctors =
    await response.Content
        .ReadFromJsonAsync<List<DoctorResponse>>();

Assert.NotNull(doctors);
Assert.NotEmpty(doctors);
```

Now you're testing both:

* HTTP response
* Response data

# 9. Testing POST Endpoint

Suppose:

```text
POST /api/doctors
```

Request:

```json
{
    "name": "Dr. Smith",
    "specialization": "Neurology"
}
```

Test:

```csharp
[Fact]
public async Task CreateDoctor_ReturnsCreated()
{
    // Arrange
    var request = new CreateDoctorRequest
    {
        Name = "Dr. Smith",
        Specialization = "Neurology"
    };

    // Act
    var response = await _client.PostAsJsonAsync(
        "/api/doctors",
        request);

    // Assert
    Assert.Equal(
        HttpStatusCode.Created,
        response.StatusCode);
}
```

This is much closer to how a real client interacts with your API.

---

# 10. Test Validation

Suppose `Name` is required.

Send:

```csharp
var request = new CreateDoctorRequest
{
    Name = "",
    Specialization = "Neurology"
};
```

Then:

```csharp
var response = await _client.PostAsJsonAsync(
    "/api/doctors",
    request);

Assert.Equal(
    HttpStatusCode.BadRequest,
    response.StatusCode);
```

Now you're testing the API's actual validation pipeline.

# 11. Database in Integration Testing

For a proper integration test, you normally don't want to modify your development/production database.

Instead:

```text
Integration Test
       ↓
Test Configuration
       ↓
Test Database
```

Common choices include:

### Option 1 — SQLite In-Memory

```text
Fast
Easy
Relational database behavior
```

### Option 2 — SQL Server Test Database

```text
More realistic SQL Server behavior
```

### Option 3 — Testcontainers

```text
Integration Test
       ↓
Docker Container
       ↓
SQL Server
```

For a professional project, **Testcontainers** can be useful when you need tests against the same database technology used in production.

Your SmartHealthcare API has authentication, so eventually you should test protected endpoints too.

For example:

```text
GET /api/doctors

```

An integration test can verify:

```text

   ↓
```

```text

   ↓

   ↓

```

You can also test authorization:

```text
Doctor role → allowed
```

# 13. Integration Test vs End-to-End Test

These are related but not exactly the same.

### Integration Test

Usually tests your application and its components together:

```text
API
 ↓
Application
 ↓
Database
```

### End-to-End Test

Tests the system from the perspective of a real user/client and can involve additional external systems:

```text
Client
 ↓
API
 ↓
Database
 ↓
External Services
```

For your .NET interview, understand the distinction but don't overcomplicate it.

# 16. Testing Pyramid

A good application normally has more unit tests than integration tests.

```text
              /\
             /  \
            / E2E\
           /------\
          /        \
         /Integration\
        /--------------\
       /                \
      /   Unit Tests     \
     /____________________\
```

In practice:

```text
Many Unit Tests
       ↓
Fewer Integration Tests
       ↓
Very Few E2E Tests
```

Why?

**Unit tests** are fast and pinpoint failures.

**Integration tests** give confidence that components actually work together.

**E2E tests** are valuable but generally slower and more expensive to maintain.
