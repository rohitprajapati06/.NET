# Unit Testing Repositories in ASP.NET Core Web API

A **Repository** is responsible for communicating with the database. In an ASP.NET Core Web API, it typically performs operations such as:

* Get data
* Insert data
* Update data
* Delete data
* Query/filter data

A typical architecture is:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
EF Core
    ↓
SQL Server
```

When testing the repository itself, the main challenge is that it depends on **EF Core/database infrastructure**.

---

## 1. Example Repository

Suppose we have:

```csharp
public interface IDoctorRepository
{
    Task<Doctor?> GetByIdAsync(Guid id);
    Task<List<Doctor>> GetAllAsync();
    Task AddAsync(Doctor doctor);
}
```

Implementation:

```csharp
public class DoctorRepository : IDoctorRepository
{
    private readonly ApplicationDbContext _context;

    public DoctorRepository(ApplicationDbContext context)
    {
        _context = context;
    }

    public async Task<Doctor?> GetByIdAsync(Guid id)
    {
        return await _context.Doctors
            .FirstOrDefaultAsync(x => x.Id == id);
    }

    public async Task<List<Doctor>> GetAllAsync()
    {
        return await _context.Doctors.ToListAsync();
    }

    public async Task AddAsync(Doctor doctor)
    {
        await _context.Doctors.AddAsync(doctor);
        await _context.SaveChangesAsync();
    }
}
```

---

# 2. What Are We Testing?

For example:

```csharp
GetByIdAsync(id)
```

We want to verify:

```text
Given doctor exists
        ↓
Repository queries database
        ↓
Correct doctor returned
```

And:

```text
Given doctor doesn't exist
        ↓
Repository returns null
```

---

# 3. Important Difference from Service Testing

Previously:

```text
Service Test
     ↓
Mock Repository
```

For repository testing:

```text
Repository Test
     ↓
Test Database
```

Because the repository's job **is to interact with the database**.

You generally shouldn't mock the repository itself when testing the repository.

---

# 4. EF Core In-Memory Database

For learning and simple repository tests, you can use:

```text
Microsoft.EntityFrameworkCore.InMemory
```

Install it in your test project:

```bash
dotnet add package Microsoft.EntityFrameworkCore.InMemory
```

Then create an in-memory database.

```csharp
var options = new DbContextOptionsBuilder<ApplicationDbContext>()
    .UseInMemoryDatabase(Guid.NewGuid().ToString())
    .Options;
```

The database exists only in memory.

```text
Test
 ↓
In-Memory DB
 ↓
EF Core
 ↓
Repository
```

No SQL Server is required.

# 5. Create Repository Test

```csharp
public class DoctorRepositoryTests
{
    private ApplicationDbContext CreateContext()
    {
        var options = new DbContextOptionsBuilder<ApplicationDbContext>()
            .UseInMemoryDatabase(Guid.NewGuid().ToString())
            .Options;

        return new ApplicationDbContext(options);
    }
}
```

Each test gets a fresh database.

# 6. Test GetByIdAsync

```csharp
[Fact]
public async Task GetByIdAsync_WhenDoctorExists_ReturnsDoctor()
{
    // Arrange
    using var context = CreateContext();

    var doctorId = Guid.NewGuid();

    context.Doctors.Add(new Doctor
    {
        Id = doctorId,
        Name = "Dr. John",
        Specialization = "Cardiology"
    });

    await context.SaveChangesAsync();

    var repository = new DoctorRepository(context);

    // Act
    var result = await repository.GetByIdAsync(doctorId);

    // Assert
    Assert.NotNull(result);
    Assert.Equal(doctorId, result.Id);
    Assert.Equal("Dr. John", result.Name);
}
```

### Flow

```text
Arrange
   ↓

   ↓

   ↓
Create Repository
   ↓
Act
   ↓
GetByIdAsync()
   ↓
Assert
   ↓
Verify Doctor
```

# 9. Test AddAsync

```csharp
[Fact]
public async Task AddAsync_AddsDoctorToDatabase()
{
    // Arrange
    using var context = CreateContext();

    var repository = new DoctorRepository(context);

    var doctor = new Doctor
    {
        Id = Guid.NewGuid(),
        Name = "Dr. David",
        Specialization = "Neurology"
    };

    // Act
    await repository.AddAsync(doctor);

    // Assert
    var savedDoctor = await context.Doctors
        .FirstOrDefaultAsync(x => x.Id == doctor.Id);

    Assert.NotNull(savedDoctor);
    Assert.Equal("Dr. David", savedDoctor.Name);
}
```

Notice that we're checking the **database state** after the repository operation.

# 10. Testing Queries

Suppose your repository contains:

```csharp
public async Task<List<Doctor>> GetApprovedDoctorsAsync()
{
    return await _context.Doctors
        .Where(x => x.IsApproved)
        .ToListAsync();
}
```

Test:

```csharp
[Fact]
public async Task GetApprovedDoctorsAsync_ReturnsOnlyApprovedDoctors()
{
    // Arrange
    using var context = CreateContext();

    context.Doctors.AddRange(
        new Doctor
        {
            Id = Guid.NewGuid(),
            Name = "Approved Doctor",
            IsApproved = true
        },
        new Doctor
        {
            Id = Guid.NewGuid(),
            Name = "Pending Doctor",
            IsApproved = false
        });

    await context.SaveChangesAsync();

    var repository = new DoctorRepository(context);

    // Act
    var result = await repository.GetApprovedDoctorsAsync();

    // Assert
    Assert.Single(result);
    Assert.Equal("Approved Doctor", result[0].Name);
}
```

This is particularly relevant to your SmartHealthcare project because you have **doctor approval status**.

# 11. In-Memory vs Real SQL Server

There is an important limitation.

The EF Core In-Memory provider is useful for basic repository tests, but it **doesn't behave exactly like SQL Server**.

For example, SQL translation and relational behavior can differ.

For more realistic database integration testing, you can use:

```text
SQLite in-memory
```

or

```text
SQL Server test database
```

For your learning progression:

```text
Beginner
   ↓
EF Core InMemory
   ↓
SQLite InMemory
   ↓
Integration Tests
   ↓
Real/Test SQL Server
```

# 12. What Should Repository Tests Cover?

| Scenario            | Example                                |
| ------------------- | -------------------------------------- |
| Get existing entity | Returns doctor                         |
| Get missing entity  | Returns null                           |
| Get all             | Returns correct collection             |
| Filtering           | Only approved doctors                  |
| Insert              | Entity is persisted                    |
| Update              | Entity values changed                  |
| Delete              | Entity removed                         |
| Relationships       | Navigation properties loaded correctly |
| Query conditions    | Correct records returned               |

# 13. Unit vs Integration Testing

There's an important terminology point.

Strictly speaking, when you're using an **EF Core In-Memory provider**, you're testing the repository with a database-like dependency rather than a completely isolated unit.

So you'll often see this categorized as a **repository/integration-style test** rather than a pure unit test.

A useful distinction is:

```text
Pure Unit Test
Service
  ↓
Mock Repository
```

versus:

```text
Repository Test
Repository
  ↓
EF Core
  ↓
In-Memory/SQLite Database
```

And a broader integration test:

```text
HTTP Request
     ↓
Controller
     ↓
Service
     ↓
Repository
     ↓
Database
```

## Interview Answer

If asked **"How do you test repositories?"**, you can say:

> "I test repository operations against a test database rather than mocking the repository itself. For basic EF Core tests, I can use an in-memory provider or SQLite in-memory database. I seed test data, execute the repository method, and verify the returned data or database state. For more realistic database behavior, I prefer integration tests with a relational test database."
