# Test Driven Development (TDD) in ASP.NET Core Web API

**Test Driven Development (TDD)** is a development approach where you **write the test before writing the actual application code**.

The core cycle is:

```text
        ┌──────────────┐
        │  Write Test  │
        └──────┬───────┘
               ↓
           🔴 RED
               ↓
       Write Minimum Code
               ↓
           🟢 GREEN
               ↓
           Refactor
               ↓
          🔵 REFACTOR
               │
               └──────→ Repeat
```

The famous TDD cycle is:

> **Red → Green → Refactor**

---

# 1. Why TDD?

Without TDD, developers commonly do:

```text
Write Code
    ↓
Test Manually
    ↓
Fix Bugs
```

With TDD:

```text
Write Test
    ↓
Write Code
    ↓
Test Automatically
    ↓
Refactor Safely
```

The important idea is that the **test defines the expected behavior before implementation**.

---

# 2. Real ASP.NET Core Example

Let's say we want to implement:

> "A doctor can be approved."

Our service should have:

```csharp
Task<bool> ApproveDoctorAsync(Guid doctorId);
```

We haven't implemented it yet.

---

# 3. Step 1 — RED

First, write the test.

```csharp
[Fact]
public async Task ApproveDoctor_WhenDoctorExists_ReturnsTrue()
{
    // Arrange
    var doctorId = Guid.NewGuid();

    var doctor = new Doctor
    {
        Id = doctorId,
        IsApproved = false
    };

    _repositoryMock
        .Setup(x => x.GetByIdAsync(doctorId))
        .ReturnsAsync(doctor);

    // Act
    var result = await _service.ApproveDoctorAsync(doctorId);

    // Assert
    Assert.True(result);
    Assert.True(doctor.IsApproved);
}
```

At this point:

```text
Test
 ↓
ApproveDoctorAsync()
 ↓
Method doesn't exist
 ↓
🔴 RED
```

The test fails.

That's **expected** in TDD.

---

# 4. Step 2 — GREEN

Now write the **minimum code necessary** to make the test pass.

```csharp
public async Task<bool> ApproveDoctorAsync(Guid doctorId)
{
    var doctor = await _repository.GetByIdAsync(doctorId);

    if (doctor == null)
        return false;

    doctor.IsApproved = true;

    return true;
}
```

Run the test again:

```text
Test
 ↓
Service
 ↓
Doctor approved
 ↓
🟢 GREEN
```

Don't try to make the code perfect yet.

The immediate goal is:

> **Make the failing test pass.**

---

# 5. Step 3 — REFACTOR

Now improve the implementation without changing its behavior.

For example:

```csharp
public async Task<bool> ApproveDoctorAsync(Guid doctorId)
{
    var doctor = await _repository.GetByIdAsync(doctorId);

    if (doctor is null)
        return false;

    doctor.IsApproved = true;

    await _repository.UpdateAsync(doctor);

    return true;
}
```

Run the tests again.

```text
🟢 Tests still pass
        ↓
Code is improved
```

That's the **Refactor** stage.

---

# 6. Add Another Requirement

Suppose we decide:

> A doctor that doesn't exist cannot be approved.

Write the test **first**:

```csharp
[Fact]
public async Task ApproveDoctor_WhenDoctorDoesNotExist_ReturnsFalse()
{
    // Arrange
    var doctorId = Guid.NewGuid();

    _repositoryMock
        .Setup(x => x.GetByIdAsync(doctorId))
        .ReturnsAsync((Doctor?)null);

    // Act
    var result = await _service.ApproveDoctorAsync(doctorId);

    // Assert
    Assert.False(result);
}
```

Initially:

```text
🔴 RED
```

Modify the implementation:

```csharp
if (doctor is null)
    return false;
```

Now:

```text
🟢 GREEN
```

Then refactor if necessary.

# 7. TDD in an ASP.NET Core Project

TDD isn't limited to services.

You can apply it to:

```text
API
│
├── Controllers
├── Services
├── MediatR Handlers
├── Repositories
├── Validators
└── Domain Logic
```

For example:

### Requirement

> "A patient cannot book an already booked availability slot."

TDD approach:

```text
Write test
    ↓
Booking an occupied slot
    ↓
Expected: exception/failure
    ↓
🔴 RED
    ↓
Implement booking rule
    ↓
🟢 GREEN
    ↓
Refactor
```

---

# 8. TDD vs Normal Development

| Normal Development                  | TDD                        |
| ----------------------------------- | -------------------------- |
| Code first                          | Test first                 |
| Tests may come later                | Tests drive implementation |
| Manual testing often used initially | Automated test immediately |
| Requirements → Code                 | Requirements → Test → Code |
| Refactoring can feel risky          | Tests provide safety net   |

TDD doesn't mean **"test everything before writing any code"**. It means development is driven by small, automated tests representing expected behavior.

---

# 9. TDD vs Unit Testing

These are **not the same thing**.

### Unit Testing

A testing technique:

```text
Test individual units
```

### TDD

A development methodology:

```text
Test
 ↓
Code
 ↓
Refactor
```

You can have unit tests without using TDD.

For example:

```text
Developer writes service
        ↓
Developer writes unit tests afterward
```

That's **unit testing**, but not necessarily TDD.

# 10. TDD with Your SmartHealthcare Project

You could develop a feature like **Cancel Appointment** using TDD.

### Requirement

> Cancel an existing appointment and release its availability slot.

### Test 1

```text
Given appointment exists
        ↓
Cancel appointment
        ↓
Status = Cancelled
        ↓
Slot.IsBooked = false
```

Write test → 🔴

Implement → 🟢

Refactor → 🔵

### Test 2

```text
Given appointment doesn't exist
        ↓
Cancel appointment
        ↓
Expected failure
```

🔴 → 🟢 → 🔵

### Test 3

```text
Given appointment already cancelled
        ↓
Cancel again
        ↓
Expected failure
```

🔴 → 🟢 → 🔵

So your development becomes:

```text
CancelAppointment
      │
      ├── Test: appointment exists
      ├── Test: appointment missing
      ├── Test: already cancelled
      └── Test: slot released
```

# 11. Benefits of TDD

### 1. Clear requirements

The test describes expected behavior.

### 2. Early bug detection

Problems are discovered while implementing the feature.

### 3. Safer refactoring

You can change the implementation and immediately run the tests.

### 4. Better design

TDD often encourages:

* Small methods
* Dependency injection
* Separation of concerns
* Loosely coupled classes

### 5. Regression protection

Existing tests make sure new changes don't break existing behavior.

---

# 12. Important Interview Answer

If an interviewer asks:

**"What is TDD?"**

You can answer:

> **"TDD is a development approach where I first write an automated test describing the expected behavior, run it and see it fail, then implement the minimum code required to make it pass, and finally refactor while keeping the tests green. This is known as the Red-Green-Refactor cycle."**

And if they ask:

**"Is TDD the same as unit testing?"**

> **"No. Unit testing is a testing technique, whereas TDD is a development methodology. Unit tests can be written after implementation, while TDD uses tests to drive the implementation from the beginning."**
