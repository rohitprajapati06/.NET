## SSO Authentication in ASP.NET Core Web API

**SSO (Single Sign-On)** allows a user to authenticate **once** with a central Identity Provider (IdP) and then access multiple applications/APIs without logging in separately to each one.

### 1. Real-Time Example

Suppose a company has:

* Employee Portal
* HR Portal
* Hospital Management API
* Admin Dashboard

Instead of maintaining separate login systems:

```text
                    ┌─────────────────────┐
                    │   Identity Provider │
                    │   (Microsoft Entra) │
                    └──────────┬──────────┘
                               │
                         User Login
                               │
              ┌────────────────┼────────────────┐
              ↓                ↓                ↓
       Employee Portal     HR Portal       Hospital API
```

The user logs in through the **Identity Provider**. Once authenticated, the applications trust the identity/token issued by that provider.

---

# 2. Main Components

### Identity Provider (IdP)

Responsible for:

* Login
* Password/MFA
* User identity
* Token issuance
* Session management

Examples:

* Microsoft Entra ID
* Okta
* Auth0
* Keycloak

### Client/Application

The application that wants the user to log in.

Example:

```text
Angular Application
      ↓
Microsoft Entra ID
      ↓
Access Token
      ↓
ASP.NET Core API
```

### Resource Server

Your ASP.NET Core Web API is typically the **resource server**.

It validates the access token and determines what the user is allowed to access.

---

# 3. SSO Flow

A simplified flow looks like this:

```text
User
 │
 │ 1. Access Application
 ↓
Frontend
 │
 │ 2. Redirect to IdP
 ↓
Identity Provider
 │
 │ 3. User logs in
 ↓
Identity Provider
 │
 │ 4. Authorization Code / Tokens
 ↓
Frontend
 │
 │ 5. Access Token
 ↓
ASP.NET Core Web API
 │
 │ 6. Validate Token
 ↓
Controller
 │
 │ 7. Return Data
 ↓
User
```

The important point is:

> **The API normally does not perform the user's login itself. It validates an access token issued by the trusted Identity Provider.**

---

# 4. SSO vs Normal JWT Authentication

You already learned JWT authentication, so this distinction is important.

### Traditional JWT setup

You might build:

```text
Login API
   ↓
Validate username/password
   ↓
Generate JWT
   ↓
Client
   ↓
API
```

Your application acts as the authentication server.

### SSO

With SSO:

```text
Client
   ↓
Identity Provider
   ↓
Access Token
   ↓
Your API
```

The Identity Provider handles authentication.

Your API mainly handles **authorization and token validation**.

---

# 5. Protocols Used for SSO

The two important protocols are:

### OAuth 2.0

Primarily deals with **authorization**.

Example:

```text
Can this application access the user's API resources?
```

### OpenID Connect (OIDC)

Built on OAuth 2.0 and provides **authentication/identity**.

Example:

```text
Who is this user?
```

For modern web applications, SSO commonly uses:

```text
OpenID Connect + OAuth 2.0
```

# 6. ASP.NET Core Web API Example

Suppose we're using **Microsoft Entra ID** as the Identity Provider.

Install:

```bash
dotnet add package Microsoft.Identity.Web
```

Then configure authentication.

### `Program.cs`

```csharp
using Microsoft.Identity.Web;

var builder = WebApplication.CreateBuilder(args);

builder.Services
    .AddAuthentication()
    .AddMicrosoftIdentityWebApi(
        builder.Configuration.GetSection("AzureAd"));

builder.Services.AddAuthorization();

builder.Services.AddControllers();

var app = builder.Build();

app.UseHttpsRedirection();

app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();

app.Run();
```

---

# 7. Configuration

`appsettings.json`:

```json
{
  "AzureAd": {
    "Instance": "https://login.microsoftonline.com/",
    "TenantId": "your-tenant-id",
    "ClientId": "your-api-client-id"
  }
}
```

The exact configuration can vary depending on your Entra setup and authentication scenario.

---

# 8. Protect an API

Use `[Authorize]`.

```csharp
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;

[ApiController]
[Route("api/[controller]")]
public class PatientsController : ControllerBase
{
    [Authorize]
    [HttpGet]
    public IActionResult GetPatients()
    {
        return Ok("Authenticated user can access patients");
    }
}
```

Without a valid access token:

```text
HTTP 401 Unauthorized
```

---

# 9. Role-Based SSO Authorization

You can also restrict APIs by role.

```csharp
[Authorize(Roles = "Admin")]
[HttpDelete("{id}")]
public IActionResult DeletePatient(Guid id)
{
    return Ok();
}
```

The flow becomes:

```text
User
 ↓
SSO Login
 ↓
Identity Provider
 ↓
Access Token
 ↓
ASP.NET Core API
 ↓
Validate Token
 ↓
Check Role
 ↓
Allow / Deny
```

If authenticated but lacking the required permission:

```text
HTTP 403 Forbidden
```

# 10. SSO Across Multiple Applications

Imagine:

```text
                    Microsoft Entra ID
                           │
                    User logs in once
                           │
          ┌────────────────┼────────────────┐
          ↓                ↓                ↓
     HR Portal       Hospital Portal    Admin Portal
          │                │                │
          └────────────────┼────────────────┘
                           ↓
                    ASP.NET Core APIs
```

When the user opens another application, the Identity Provider already has an authenticated session, so the user generally doesn't need to enter their credentials again.

That's the **Single Sign-On** experience.

# 11. Important Terms for Interviews

| Term                  | Meaning                                                          |
| --------------------- | ---------------------------------------------------------------- |
| **SSO**               | Authenticate once and access multiple applications               |
| **Identity Provider** | Performs authentication and issues identity/security tokens      |
| **IdP**               | Short form of Identity Provider                                  |
| **OAuth 2.0**         | Authorization framework                                          |
| **OpenID Connect**    | Authentication/identity layer built on OAuth 2.0                 |
| **Access Token**      | Token used to access an API                                      |
| **ID Token**          | Contains information about the authenticated user/client session |
| **Resource Server**   | API that protects resources                                      |
| **Client**            | Application requesting access                                    |
| **401**               | Authentication missing/invalid                                   |
| **403**               | Authenticated but not authorized                                 |

## SSO vs JWT — Important Interview Point

Don't think of them as alternatives:

```text
SSO
 ↓
Authentication architecture / user experience

JWT
 ↓
Token format commonly used for carrying claims
```

An SSO system can issue **JWT access tokens**, and your ASP.NET Core API can validate those tokens.

### Interview answer

> **SSO is an authentication mechanism where a user authenticates once with a central Identity Provider and can then access multiple trusted applications without logging in separately. In ASP.NET Core Web API, the API usually acts as a resource server. It validates access tokens issued by an Identity Provider such as Microsoft Entra ID, Auth0, Okta, or Keycloak, and then applies authorization policies or roles to determine whether the user can access a resource. Modern SSO implementations commonly use OpenID Connect for authentication and OAuth 2.0 for authorization.**
